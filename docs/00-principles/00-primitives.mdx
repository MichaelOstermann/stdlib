Wherever possible, this library focuses on exposing well designed primitives: Building blocks that allow you to cover your own scenarios by building on top, instead of hiding the complexity behind options.

## Low-level primitives, high-level abstractions

It is tempting to try to come up with a declarative interface that can one-shot all the possibilities under the sun, only to find later on that a new scenario we didn't think of is not only hard, it can often be impossible to implement.

Consider your average command line tool out there:

```ts
command({
    name: "foo",
    flags: {
        bar: {...},
        baz: {...},
    },
})
```

While this is an easy to use interface, this design makes it impossible to declare that either `bar` or `baz` should be used, but not both simultaneously (eg. you can either read a file via a `--path` option or pass something to STDIN, but not both).

So inevitably, bit by bit such an interface will become more complex:

```ts
command({
    name: "foo",
    flags: {
        bar: { conflict: "baz" },
        baz: { conflict: "bar" },
    },
})
```

And then on another day you'll come to find that there can be multiple conflicts:

```ts
command({
    name: "foo",
    flags: {
        bar: { conflicts: ["baz"] },
        baz: { conflicts: ["bar"] },
    },
})
```

On a side note: Typing `conflicts` so that it only accepts the names of the other flags is already a struggle, the easy way out is `string[]`. If something becomes difficult to implement type-wise in TypeScript, it is a pretty good sign that something somewhere went wrong.

It is not really about the likelihood of these things happening, it is more about _once_ they happen then things can get pretty painful, and something somewhere _will_ happen one day. A few of those somethings:

- Required and optional flags, sometimes depending on which other flags were used
- Flags shared between commands (`--json`)
- Interactive input (prompts, selects, confirmations), eg. for missing values, and failing without a terminal
- Different behavior for agents, in CI, or when piped, for input and output alike: prompts, colors, JSON, help, even which commands exist
- Input from stdin
- Help that leaves out the flags already given
- Help for commands that only group others (`members --help`)
- Help and errors in other languages
- A full help for agents, every command at once (like `llms-full.txt`)
- Mistyped commands and flags: suggest the right one, or run it anyway (`mmbers` for `members`)
- Shell completion for commands, flags and values (eg. fetched from a server)
- Commands that only exist at runtime
- Calling commands from code (RPC), and tests with their own argv

We think that one of the best things we can do is to provide two layers of abstractions:

### Low-level primitives

```ts
command({
    name: "foo",
    flags() {
        return {}
    },
})
```

Simply by turning this into a plain function you now gained the ability to parse arguments however you'd like. Not only that but this is probably the easiest thing to implement as a library author.

Let's take a look at the process of parsing arguments next. Some of what you might run into:

- `--foo bar`, `--foo=bar`, and esbuild's `--foo:bar`
- `--foo bar`: a flag with a value, or a flag and a positional?
- Bundled short flags (`-abc`), and values attached to them (`-n5`)
- `-5`: a value or a flag?
- `--foo` and `--no-foo`
- Repeated flags (`--tag a --tag b`) and lists (`--tag a,b`)
- Nested flags (`--foo.bar` into `{ foo: { bar } }`)
- Everything after `--` is positional
- Several words as one positional, or as several (`bun run xyz foo bar`)

The best thing we could come up with is expressing them as a doubly linked list:

```ts
const tokens = Tokens(process.argv.slice(2))

while (tokens.head) {
    console.log(tokens.head.index) // The position of the argument
    console.log(tokens.head.value) // The value of the argument
    console.log(tokens.head.next) // Peek ahead
    console.log(tokens.head.prev) // Peek behind
    tokens.head.remove() // Consume arguments
}
```

A doubly linked list allows you to search through its values, peek what's ahead/behind and mark arguments as consumed by removing them.

### High-level abstractions

The above is flexible and simple enough to cover (probably) everything you could possibly want, but we lost the "easy to use" aspect from before.

What we can do however is to provide an opinionated abstraction that can (hopefully) make the 99% use case easy to use again:

```ts
// A high-level abstraction over Tokens(),
// it can't do everything, but it can cover most things:
const parseFoo = CLI.flag({
    name: "foo",
    alias: "f",
    ...
})

// Back to what we had before, returns a function
// that can be passed to command():
const flags = CLI.flags({
    bar: {...},
    baz: {...},
})

command({
    name: "foo",
    flags,
})
```

You get the best of both worlds: You get an easy to use API, and when it should fail you, the story isn't over just yet.

## More examples

### Hotkeys

The possibilities for what you might want out of a hotkey/shortcut library are seemingly endless:

- Per-hotkey arbitrary metadata
- Programmatically triggering shortcuts
- Binding to document, a specific focusable element, React refs, React callbacks, third-party libraries
- Listening to keydown, keyup, keypress, input, beforeinput, with or without `{ capture: true }`
- Resolving shortcut conflicts
- Building a UI around currently bound shortcuts
- Recording and replaying keypresses
- Shortcut sequences, of which there are several possible behaviors
- Grouping shortcuts together into scopes, enabling/disabling scopes
- Different keybindings enabled only for macOS/Windows
- Support for sticky keys for accessibility reasons
- Pausing and resuming event listeners
- Ignoring keys during IME composition
- Support for user provided shortcut configurations
- Telemetry (which shortcuts are used, which ones were attempted but not implemented)

So the first thing you'd want is a good type definition to express any keystroke:

```ts
export interface Keystroke {
    alt: boolean
    ctrl: boolean
    key: string
    meta: boolean
    shift: boolean
}
```

And secondly a good shortcut parser:

```ts
const keystrokes = Shortcut.parse("ctrl+k") // Keystroke[]
const shortcut = Shortcut.serialize(keystrokes)
```

And lastly the hard part, figuring out whether a keyboard event matches a shortcut, regardless of keyboard layout, IME composition or sequences:

```ts
window.addEventListener("keydown", (event) => {
    if (Shortcut.matches("mod+k", event)) openPalette()
})
```

Everything from the list above is now just your own code around that `if`, e.g.:

```ts
window.addEventListener("keydown", (event) => {
    // Scopes:
    if (scope !== "editor") return
    // User provided shortcut configurations:
    if (Shortcut.matches(config.palette, event)) return openPalette()
    // Telemetry for shortcuts that were attempted but not implemented:
    track(Shortcut.serialize([Shortcut.fromEvent(event)]))
})
```

And for per-hotkey arbitrary metadata, you can extend the type of a binding yourself:

```ts
declare module "@monstermann/stdlib-web" {
    interface ShortcutBinding {
        description?: string
    }
}
```

The library has a few more helpers, but these three are the core.

### Popover

Instead of a middleware system with options for every case, the first thing we expose is a primitive for describing a position:

`Rect` `{ top, left, width, height }`, including simple helpers like `Rect.translateY(rect, 100)`

Positioning a popover now becomes a single function, where everything going in and coming out is a `Rect`:

```ts
{
    position: ({ anchor, boundary, floating }) => {
        // Below the anchor, horizontally centered:
        const below = Rect.moveTopTo(floating, Rect.bottom(anchor) + 4)
        return Rect.setCenterX(below, Rect.centerX(anchor))
    }
}
```

Everything else is code you write around it.

Positioning libraries often export dozens of types: Different shapes for a rectangle (coordinates, dimensions, sides, coordinates with dimensions, coordinates with dimensions and sides, a pair of rects), more than a handful of different sets of options, middleware state, etc. Here it is one: `Rect`.

We ship additional utility functions, mostly to cover our own scenarios:

```ts
{
    position: (measurements) => {
        // Given an anchor, which sides have more room?
        // Often this is more than enough to figure out
        // whether a popover should be placed e.g. below
        // or above the anchor:
        const room = Placement.room(measurements)
        room.horizontal // "left" | "right"
        room.vertical // "up" | "down"
    }
}
```

There is no reasonable way to ship a "standard" positioning algorithm that one-shots everything, a few examples:

- Sometimes popovers can dynamically change height and what should happen here (Should it flip to the opposite side when it no longer fits? Should we fake extra height and compute the ideal position ahead of time?) is ambiguous
- The rules for the ideal position of a toolbar in rich text editors are complicated, for example generally speaking as close to the caret as possible, but without overlapping too much text behind it

### Concurrency

Libraries for async work tend to come as a family: a queue, a pool, a mutex, a lock per key, a wrapper that limits how often a function runs at once. Each has its own package and its own options.

They are all the same thing: a few functions run, the others wait for their turn. So there is one primitive, `Semaphore`, with one method, `run`:

```ts
// A queue: one after the other, in the order they came in.
const queue = Semaphore({ concurrency: 1 })
await queue.run(() => save(document))

// A pool: up to 4 at the same time.
const pool = Semaphore({ concurrency: 4 })
await pool.run(() => fetch(url))

// A lock: one at a time per key, different keys do not wait for each other.
const locks = Semaphore({ concurrency: 1 })
await locks.run(path, () => migrate(path))

// Bounded: fails instead of letting more than 100 wait.
const hashing = Semaphore({ concurrency: 2, maxWaiting: 100 })
const hash = await hashing.run(() => hashPassword(password)) // Result<string, SemaphoreFullError>

// Waiting until nothing is running or waiting:
await pool.idle()
```

Everything else is code you write around `run`. Say you want a queue that can drop everything it holds, and where tasks expire:

```ts
function Queue(options: { ttl?: number } = {}) {
    const queue = Semaphore({ concurrency: 1 })
    let controller = new AbortController()

    return {
        add: <T>(fn: (signal: AbortSignal) => Promise<T>) => {
            const signal = options.ttl
                ? AbortSignal.any([
                    controller.signal,
                    AbortSignal.timeout(options.ttl),
                ])
                : controller.signal
            return queue.run(() => fn(signal), { signal })
        },
        clear: () => {
            controller.abort()
            controller = new AbortController()
        },
    }
}

const downloads = Queue({ ttl: 30_000 })
await downloads.add((signal) => fetch(url, { signal }))
```

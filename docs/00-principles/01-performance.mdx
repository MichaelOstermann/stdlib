title: Performance

This monorepo addresses performance almost fanatically, including spending hundreds of USD worth of tokens to:

- Find performance improvements ad-hoc ("Pump perf, make no mistakes" - you never know)
- Orchestrate sub-agents for experiments
- Learn techniques from 3rd-party libraries

If anything can be shaved off, and neither readability nor simplicity are sacrificed in doing so (which is often the case), it gets shipped. If performance can be increased by reducing the API surface area, it might get shipped.

Numbers are per call, in V8 (Node 26). The details, JavaScriptCore (Bun) included, are in `benchmarks/` (`bun run benchmarks`).

## Why

There are two extremes: Not thinking about performance at all, or thinking about it *too much*.

Ideally we would find a balance between the two on a case-by-case basis, which is hard, especially because it has to hold up over time: What was fast enough yesterday might suddenly become too slow tomorrow.

When we don't think about performance at all, our products become slower and slower over time, and we get used to it, we might not even notice it.

When we think about it too much, sleepless nights thinking about how to pump performance, historically that would have taken a lot of time, while turning code into something that can only be described as an abomination (and earned us a "premature optimization" talk).

We also run into the danger of optimizing the wrong thing: Improving few Effects reading many Signals, which is unrealistic, while decreasing the performance of many Effects reading few Signals, which is much more realistic.

Today, coding agents make this much easier and faster to explore than ever before, even if they have to be steered carefully, away from the wrong case like above.

The worst performance problem is death by a thousand cuts: Not a single particular thing that sticks out in profiles, but dozens of slightly unoptimized things that compound, which nobody wants to touch.

The more code we ship that is performance considerate, the more we can afford to be sloppy elsewhere.

## Memory allocations

In JavaScript, more often than not functions create a shallow copy even when nothing changed:

```ts
const a = [1, 2, 3]
const b = a.map(i => i)
a === b // false
```

Sometimes this can be a deal breaker, for example in React and signal libraries, all of which depend on `===` checks to skip work.

So now you'll come to find that libraries often ship something like this:

```ts
function map(target, fn) {
    let didChange = false;
    const result = target.map((before) => {
        const after = fn(before);
        didChange ||= before !== after;
        return after;
    });
    return didChange ? result : target;
}
```

While this implementation does return the original reference when possible, it still creates a copy every time, even when nothing changed.

In JavaScript, these allocations don't show up where they happen: They end up as GC time spread across the whole profile, which no single function owns.

We generally speaking try to avoid this by doing something similar to:

```ts
function map(target, fn) {
    let copy;
    for (let i = 0; i < target.length; i++) {
        const before = target[i];
        const after = fn(before);
        if (before === after) continue;
        // Copy once now that we know we are actually going to write:
        copy ??= [...target];
        copy[i] = after;
    }
    return copy ?? target;
}
```

For the keen eye: There is a difference in behavior when using sparse arrays. If you have a serious use case for sparse arrays, you probably shouldn't hand them to any 3rd-party library anyway.

| | Copy first | Copy on write |
|---|---|---|
| 10 items, nothing changed | 30 ns · 232 B | 3 ns · 0 B |
| 10 items, something changed | 29 ns · 232 B | 27 ns · 128 B |
| 1000 items, nothing changed | 2.0 µs · 8.3 KB | 187 ns · 15 B |
| 1000 items, something changed | 2.0 µs · 8.2 KB | 875 ns · 8.2 KB |

## Build-time optimizations

Our `stdlib-transform` uses the fantastic [oxc](https://oxc.rs/) toolchain to provide several build-time optimizations, in some cases offering 0-cost abstractions. oxc is fast enough to blast through 1000 files in less than a second, so there is no particular reason to not do that.

The main challenge here is that code needs to be designed around this: As of today, a transformer can't easily use type information, so it has to understand what's happening purely by looking at the syntax.

A few examples:

### `match`

Our pattern matching tool featuring type-level exhaustiveness checks, greatly inspired by [ts-pattern](https://github.com/gvergnaud/ts-pattern):

<Tabs sync={false} hash={false}>
<Tab title="Before">

```ts
type Shape =
    | { kind: "circle"; radius: number }
    | { kind: "square"; size: number };
    
const label = (value: Shape | null) => match(value)
    .case(null, "Nothing")
    .shape({ kind: "circle" }, "A circle")
    .shape({ kind: "square" }, "A square")
    .unwrap()
```

</Tab>
<Tab title="After">

```ts
import { throwUnmatched } from "@monstermann/stdlib/internals/match/throwUnmatched.mjs";

const label = (value: Shape | null) =>
    value === null ? "Nothing"
    : typeof value === "object" && value !== null && value.kind === "circle" ? "A circle"
    : typeof value === "object" && value !== null && value.kind === "square" ? "A square"
    : throwUnmatched(value);
```

</Tab>
</Tabs>

| | `match` | `match`, compiled | ts-pattern |
|---|---|---|---|
| Per call | 35 ns · 152 B | 2 ns · 0 B | 187 ns · 1.7 KB |

This only works because `match` has `.case()`, `.shape()` and `.cond()` instead of a single `.with()`: Whether `.with(x)` compares a value, a shape or runs a predicate depends on the type of `x`, so it can't be compiled, while each of ours can only mean one thing. [pattycake](https://github.com/aidenybai/pattycake), a compiler for ts-pattern, has been stuck as "highly experimental" since early 2024, falling back to ts-pattern for whatever it can't compile.

### `Object.setPath`

Other functions like `Object.setPath` also sometimes have an opportunity to be optimized into handwritten code:

<Tabs sync={false} hash={false}>
<Tab title="Before">

```ts
const next = Object.setPath(state, "user.settings.theme", "dark")
```

</Tab>
<Tab title="After">

```ts
const next = setPath0(state, "dark")

function setPath0(t, v) {
    const t0 = t.user, t1 = t0.settings, t2 = t1.theme
    if (Object.is(t2, v) && "theme" in t1) return t
    return { ...t, user: { ...t0, settings: { ...t1, theme: v } } }
}
```

</Tab>
</Tabs>

| | `Object.setPath` | `Object.setPath`, compiled |
|---|---|---|
| Nothing changed | 36 ns · 32 B | 2 ns · 0 B |
| Something changed | 97 ns · 233 B | 31 ns · 200 B |

The price is bundle size: About 150 bytes per path, minified, once per module that uses it.

### pipe

`pipe` is another example that can be optimized:

<Tabs sync={false} hash={false}>
<Tab title="Before">

```ts
const result = pipe(value, (v) => v + 1, (v) => v * 2)
```

</Tab>
<Tab title="After">

```ts
const result = ((value + 1) * 2)
```

</Tab>
</Tabs>

Depending on what you do, engines can inline functions already, so the boost is there, but tiny:

| | `pipe` | `pipe`, compiled |
|---|---|---|
| Cheap steps | 1.4 ns · 0 B | 0.8 ns · 0 B |
| Bigger steps | 63 ns · 264 B | 60 ns · 208 B |

Contrary to the previous example of `Object.setPath` which slightly increases bundle size, this one comes at absolutely no cost, so we left it in.

## Engine details

Smaller things, which only show once you measure them the way an app uses them.

### Computed properties

```ts
const copy = { ...target, [key]: value }

const copy = { ...target }
copy[key] = value
```

The above performs differently depending on whether engines treat `copy` as monomorphic, polymorphic or megamorphic:

| | Computed property | Spread, then assign |
|---|---|---|
| One shape | 10 ns · 40 B | 10 ns · 40 B |
| Four shapes | 206 ns · 242 B | 37 ns · 240 B |

A naive benchmark would test `Object.set(foo, "bar", true)` only, where the engine sees only one shape, however that's not what is going to happen.

### `Object.is`

V8 slows down when comparing two objects with `===` instead of `Object.is`, whereas other types stay consistently fast. Mapping over 1000 objects where nothing changes:

| | `===` | `Object.is` |
|---|---|---|
| 1000 objects | 790 ns · 6 B | 186 ns · 1 B |

### Switching data structures by size

Sometimes performance can be boosted by switching between data structures depending on the size of the input, for example between an `Array` and a `Set`.

`Array.removeAll(target, values)` removes every occurrence of each of `values`. With up to 4 values, it checks each element against them with `includes`. With more, it builds a `Set` of them first, which costs something up front but answers faster:

| | `includes` | `Set` |
|---|---|---|
| 2 values | 415 ns · 2.4 KB | 427 ns · 2.6 KB |
| 4 values | 491 ns · 2.4 KB | 446 ns · 2.6 KB |
| 8 values | 641 ns · 2.4 KB | 520 ns · 2.6 KB |
| 32 values | 1.5 µs · 1.2 KB | 768 ns · 2.5 KB |

## What didn't work

### Mutation fast paths

We tried shipping opt-in mutation as a fast path, twice. First with [remmi](https://github.com/MichaelOstermann/remmi), which lets every function mutate inside a `withMutations` scope, copying each value only the first time it gets changed:

```ts
const before = []

const after = withMutations(() => {
    const a = push(before, 0) // Copies
    const b = push(a, 1) // Mutates
    const c = push(b, 2) // Mutates
    return c
})

before // []
after // [0, 1, 2]
```

Then with a `{ mut: true }` option on individual functions, for arrays we already own:

```ts
const tasks = Array.map(all, toView)
Array.filter(tasks, isOpen, { mut: true })
Array.filter(tasks, isVisible, { mut: true })
```

Neither beat plain mutation. From remmi's own benchmarks, pushing values into an empty array (Apple M1 Max, Node 24):

| | Time per op |
|---|---|
| Mutation | 34 ns |
| remmi (`withMutations`) | 148 ns |
| Copy + mutation | 253 ns |
| mutative | 7 µs |
| immer | 12 µs |

The big win remmi gave us came from a single loop, which applied hundreds of updates one at a time and copied the entire array for each one. Copying once by hand did the same.

So there is no mutation mode to opt into. Instead look at hot paths, look at anything that loops, and optimize those by hand. A copy nobody else holds a reference to can just be changed with plain JavaScript:

```ts
const next = [...tracks]
for (const track of updates) next[index.get(track.id)] = track
```
